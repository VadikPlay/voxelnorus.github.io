# Как добавить новый проект

Три команды и один файл.

```bash
cp data/projects/01-gatekit.json data/projects/02-мой-проект.json
nano data/projects/02-мой-проект.json
python3 build.py
```

Порядок на странице — по имени файла. Хочешь новый проект первым — назови его `00-`,
или переименуй остальные. Префикс в имени файла на сайт не попадает, показывается
только `slug`.

---

## Поля

Любое поле с `en` / `ru` — двуязычное. Можно оставить только `en`: русская версия
подставит английский текст, и сайт не сломается.

| Поле | Обязательно | Что это |
|---|---|---|
| `slug` | да | Адрес страницы: `p/<slug>.html`. Только латиница и дефисы |
| `title` | да | Название проекта |
| `subtitle` | да | Одна строка: что это. Видна в списке и в поиске Google |
| `year` | да | Год |
| `kind` | да | Тип: `Open source · MIT`, `Client project`, `Personal` |
| `tags` | да | Технологии, 4–7 штук. Больше — превращается в кашу |
| `summary` | да | 2–3 предложения для карточки в списке |
| `problem` | да | Задача с точки зрения ЗАКАЗЧИКА, не разработчика |
| `approach` | да | Массив блоков `{title, body}` — как решено |
| `proof` | нет | Числа: `{value, label}`. Только проверяемые |
| `proof_note` | нет | Абзац о том, как это проверялось |
| `delivers` | нет | Список того, что умеет |
| `links` | нет | `{label, url, primary}`. `primary: true` — тёмная кнопка |
| `honesty` | нет | Когда это НЕ нужно. Не пропускай — см. ниже |
| `featured` | нет | Пока ни на что не влияет, задел на будущее |

## Как писать кейс, который продаёт

Заказчик читает кейс, чтобы ответить себе на один вопрос: «этот человек справится с
МОЕЙ задачей?». Всё остальное — шум.

**`problem` пиши от боли заказчика, не от технологии.**
Плохо: «Нужно было реализовать парсер на Python с асинхронными запросами».
Хорошо: «Владелец канала вручную сверял поступления в кошельке с юзернеймами и держал
таблицу со сроками. На 200 подписчиках это полноценная работа».
Первое интересно тебе. Второе — тому, кто платит.

**В `approach` объясняй развилки, а не перечисляй инструменты.**
Список технологий пишут все, он не отличает тебя ни от кого. Отличает объяснение, почему
выбрано так: «У TRC20-перевода нет memo, поэтому каждый счёт получает уникальную сумму».
Такой абзац показывает, что ты думал, а не собрал из туториала.

**Опиши хотя бы одну трудность и как ты её нашёл.**
В кейсе Gatekit описан баг, который вылез только на живом вызове API: TronGrid при
превышении лимита отдаёт HTTP 200 с полем Error вместо 429, и наивный код принял бы это
за «переводов нет». Это выглядит сильнее, чем идеальная история, по двум причинам:
идеальным историям не верят, и это доказывает, что ты проверял на реальности, а не
только «у себя работает».

**`proof` — только то, что можно пересчитать.**
Число тестов, строк, дней до сдачи — можно. «Увеличил конверсию на 40%» без доступа к
чужой аналитике — нельзя, и первый же внимательный заказчик это почувствует. Нет чисел —
убери блок целиком, это честнее пустого.

**`honesty` заполняй всегда.**
Раздел «когда это не нужно» — самый недооценённый в портфолио. Все продают через
«вам это необходимо». Тот, кто пишет «если у вас вот такая ситуация, возьмите вот то,
оно бесплатное», выглядит как консультант, а не как продавец. Именно к такому приходят
с бюджетом.

## Что делать с клиентскими проектами под NDA

Большинство заказов нельзя показать целиком. Показывай форму, а не содержимое:

- `title`: «Telegram-бот для сети барбершопов» вместо названия клиента
- `kind`: `Client project · NDA`
- `problem` и `approach` — можно почти всё: боли и инженерные решения обычно не секрет
- `proof` — относительные числа вместо абсолютных: «сократил ручную работу с 6 часов в
  неделю до 20 минут» вместо выручки клиента
- `links` — убери или оставь только на публичную часть
- Добавь в `honesty` строку, что код под NDA и показать его нельзя

Такой кейс работает: заказчик видит, что ты умеешь, и одновременно видит, что чужие
секреты ты не выкладываешь. Второе для него важнее, чем кажется.
