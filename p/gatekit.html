Gatekit

Telegram paid-subscription bot with direct USDT payments

Python aiogram 3 USDT TRC20 TON SQLAlchemy Docker pytest
SUMMARY

A self-hosted bot that sells access to a private Telegram channel and takes payment straight into the owner's own wallet. Non-custodial: it holds no private keys and never moves funds — it only reads the public chain to learn that a payment landed.

THE PROBLEM

The problem

Owners of paid Telegram channels either give a percentage to a hosted platform, or run the money side by hand: checking a wallet for incoming transfers, matching them to usernames, adding members manually, keeping a spreadsheet of expiry dates, and remembering to remove people who stopped paying. At 50 payments a month that is a part-time job; at 200 it is a full-time one.

HOW IT WAS BUILT

How it was built

01

The problem with no memo field

A TRC20 transfer carries no comment field, so if two subscribers each send 39.00 USDT to the same wallet, the chain cannot tell you who is who. Custodial services solve this by holding the money in their own account. Gatekit solves it with arithmetic: every invoice gets a unique amount — 39.00 becomes 39.004271, where the last digits identify the invoice. Under one cent of variance, 9999 unique slots, and no custody.

02

Refusing to guess

Matching is exact: a rounded 39.00 does not satisfy an invoice for 39.004271. It is never auto-credited — it surfaces in the admin panel with the sender address and transaction id, and a human decides. A transaction id can only ever be credited once, so a re-read chain page cannot grant two subscriptions.

03

Five guards before anyone loses access

One wrongly removed subscriber costs more than a year of saved fees — the chat sees it and people churn. So removal is not an 'if expired then kick' branch. A safe mode that removes nobody and only reports is on by default; there is a grace period after expiry; anyone who paid inside the protection window is never removed whatever the dates say; every action is idempotent so restarts cannot double-act; and an optional mode makes an admin confirm each removal. Every decision — including refusals to remove — is written to an append-only audit log.

04

A bug only a live call could find

Testing against the real TronGrid API exposed something the documentation does not mention: without an API key the quota is about one request per second, and exceeding it returns HTTP 200 with an 'Error' field rather than a 429. Parsed naively that looks like 'no incoming transfers' — meaning the bot would silently miss payments. The client now throttles itself, treats that response as a retryable failure, and raises rather than reporting an empty result, so a rate limit can never be mistaken for nobody having paid. There is a regression test for it.

WHAT IT DOES

What it does

  • Subscriber flow: plans, invoice with the exact amount, automatic confirmation, single-use invite link
  • Renewal reminders 3 days and 1 day before expiry; early renewal stacks days instead of resetting them
  • Admin panel inside the bot: revenue, subscribers, who is lapsing, CSV export, manual grant/extend/revoke, broadcast, per-user audit trail
  • USDT on TRON as the production rail, TON as a second one matched by payment comment
  • Bilingual interface (English and Russian), one-command Docker deploy, systemd unit included
WHEN NOT TO USE IT

When not to use it

Gatekit is not always the right tool, and its README says so: Telegram's own Star Subscriptions are free and native, and hosted platforms start at a few percent per sale. Self-hosting is worth it when your subscribers already hold USDT, you want the money in your own wallet with no cut and no hold period, or you need logic a hosted product will not build for you.
